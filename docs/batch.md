# Пачки патчей

Пачка — несколько патчей, которые нужно применить вместе и в определённом порядке: в один workspace
или в разные workspace одной машины. Например, нейросеть подготовила изменения для трёх проектов, или
три патча одного проекта, собранных друг за другом.

```text
batch_YYYYMMDD_HHMMSS_slug.zip → склад (devctl inbox) → devctl batch plan → devctl batch start
```

## Точка опоры

У одиночного патча опора — workspace и его `patches/`. У пачки опора — машина: реестр workspace в
пользовательском конфиге и склад патчей ([patch-intake.md](patch-intake.md)). Поэтому пачку кладут в
склад (`incoming/`) или передают командам путём, а workspace в ней называют по id из реестра.

Реестр заполняется один раз:

```bash
devctl workspace scan --register      # найти все workspace под ~ и занести их в реестр
devctl workspace list --for-agent     # отдать нейросети вместе с devctl
```

`list --for-agent` сообщает нейросети id, ветку и HEAD каждого workspace. Без HEAD пачку нельзя собрать
против верной базы.

## Формат

```text
batch_20261007_120000_ring-r1.zip
  batch.json
  patches/
    patch_20261007_120000_web-x.zip
    patch_20261007_120100_mobile-y.zip
    patch_20261007_120200_devctl-z.zip
  BATCH_SUMMARY.md      # необязателен; devctl не читает
```

Внутри — обычные патчи ([patch-format.md](patch-format.md)) без изменений формата.

```json
{
  "formatVersion": 1,
  "batchId": "2026-10-07-ring-r1",
  "title": "Кольцо устройств: R1",
  "requiresDevctl": ">=0.9.0",
  "push": "after-all",
  "items": [
    {"patch": "patches/patch_20261007_120000_web-x.zip", "workspace": "p2p-kanban", "expectedHead": "749b3d0"},
    {"patch": "patches/patch_20261007_120100_mobile-y.zip", "workspace": "p2p-kanban"},
    {"patch": "patches/patch_20261007_120200_devctl-z.zip", "workspace": "devctl", "expectedHead": "301384c"}
  ]
}
```

| Поле | Значение |
| --- | --- |
| `formatVersion` | ровно `1` |
| `batchId` | непустая строка; попадает в трейлер коммитов `Devctl-Batch` |
| `title` | необязательное название |
| `requiresDevctl` | `>=X.Y.Z`, `>X.Y.Z`, `==X.Y.Z` или `X.Y.Z` (то же, что `>=`). Старый devctl откажется от пачки целиком |
| `push` | `after-all` (по умолчанию) — push всех workspace только когда прошли все патчи; `each` — push после каждого патча, как у `start`; `none` — без push |
| `items[].patch` | путь патча внутри пачки; имена файлов в пачке не повторяются |
| `items[].workspace` | id или имя workspace из реестра этой машины |
| `items[].expectedHead` | SHA, против которого собран патч. Допустим только у **первого** патча каждого workspace: HEAD для следующих появится после применения предыдущих. То же можно указать в манифесте патча как `base.expectedHead` |

Порядок применения — порядок `items`. Связи между патчами одного workspace можно продублировать в их
манифестах через `base.after`; `plan` проверит, что каждый такой патч либо уже в истории, либо стоит в
пачке выше.

## plan

`devctl batch plan [пачка]` ничего не меняет. Для каждого патча:

- манифест и пути корректны;
- workspace есть в реестре и доступен;
- патч ещё не применён (применённые помечаются и при `start` пропускаются);
- для первого патча workspace: дерево чистое, ветка из `base.branch`, HEAD совпадает с `expectedHead`;
  при включённом push — remote не ушёл вперёд, а локально впереди только коммиты этой же пачки;
- `base.after` выполнен историей или пачкой выше;
- нужные команды есть в `PATH`, каталоги проверок существуют или создаются патчами пачки;
- в `patches/` нет другого файла с тем же именем.

Проблемы печатаются по патчам; код возврата 2, если хоть одна есть.

## start

1. Повторяет `plan`. Если есть хоть одна проблема — останавливается, ничего не тронув.
2. Раскладывает патчи в `patches/` своих workspace и сверяет SHA-256.
3. Применяет их по порядку обычным `devctl start --patch <файл>`: со снимками, проверками, отчётами,
   автооткатом упавшего патча и копией в `UserTestSpace`. При `push: after-all` каждый `start` идёт
   без push. Коммиты получают трейлер `Devctl-Batch: <batchId>`.
4. Если все патчи прошли и `push: after-all`, делает push каждого затронутого workspace (политика
   push workspace по-прежнему решает: `git.autoPush: false` его отключает).
5. Записывает запуск в `batch_index.json`; пачку из склада после успеха переносит в `imported/`.

Это ближайшее к атомарности, что возможно между разными Git-репозиториями: откатить уже отправленный
коммит в чужом remote нельзя, а неотправленный — можно.

### Если патч упал

Упавший патч откатывается, как при обычном `start`, и удаляется из `patches/`. Патчи, применённые до
него, остаются локальными коммитами без push. `devctl batch status` показывает, где остановились.
Дальше два пути:

- исправить и запустить пачку снова: уже применённые патчи пропустятся, предполётная проверка
  разрешит локальные коммиты этой же пачки;
- откатить всё: `devctl batch reset --yes`.

## status

`devctl batch status [batchId|runId]` — последний запуск: статус каждого патча, коммиты, HEAD каждого
workspace до пачки и результат push.

## reset

`devctl batch reset [batchId|runId]` показывает план отката, `--yes` выполняет его: в каждом
затронутом workspace `git reset --hard <HEAD до пачки>` и `git clean -fd`, в журнал `state.json` — записи
`reverted`, разложенные патчи удаляются из `patches/` (`--keep-patches` их оставит). Workspace, в
который пачка уже отправлена, откатывать отказывается: исправление в таком случае — новый патч.

## Чего пачка не делает

- Не объединяет репозитории и не делает транзакций между ними сверх «push в конце».
- Не знает о правилах конкретного проекта (доски, направления, контракты): их проверяют `checks` в
  манифестах патчей.
- Не нужна для одиночного патча: `patches/` и `devctl start` работают как раньше.
