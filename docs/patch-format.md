# Формат патча

Патч — zip-архив, который кладут в `patches/` и применяют командой `devctl start`.

```text
patch_YYYYMMDD_HHMMSS_slug.zip
  manifest.json         # обязателен, в корне архива
  files/                # содержимое накладывается поверх проекта
    path/inside/project.ext
  PATCH_SUMMARY.md      # необязателен
  reports/              # необязателен; devctl не читает
```

Имя файла может быть любым, лишь бы оканчивалось на `.zip`. Метка `patch_YYYYMMDD_HHMMSS_` в имени
помогает упорядочить патчи, когда время изменения файлов совпадает.

## Что делает применение

1. Удаляет пути из `apply.delete`.
2. Копирует каждый файл из `files/` в проект по тому же относительному пути, перезаписывая существующие.

Патч описывает итоговое содержимое файлов целиком: диффов и частичных правок в формате нет.

## manifest.json

```json
{
  "formatVersion": 1,
  "patchId": "2026-05-05-demo-change",
  "title": "Короткое название",
  "summary": "Что меняется и зачем — одним-двумя предложениями.",
  "createdAt": "2026-05-05T12:00:00Z",
  "base": {"branch": "main", "expectedHead": "749b3d0", "after": ["2026-05-04-previous-change"]},
  "apply": {
    "filesRoot": "files",
    "delete": [{"path": "docs/old.md"}, {"path": "legacy", "recursive": true}]
  },
  "checks": [
    {"name": "Тесты", "cwd": ".", "command": "python -B -m unittest discover -s tests", "timeoutSeconds": 300}
  ],
  "commit": {"message": "feat: demo change"},
  "archive": {"nameSlug": "demo-change"}
}
```

### Обязательные поля

| Поле | Требование |
| --- | --- |
| `formatVersion` | ровно `1` |
| `patchId` | непустая строка; уникальна в пределах проекта |
| `title`, `summary` | непустые строки |
| `apply` | объект |
| `commit.message` | непустая строка (без неё обойтись можно только при `commit.enabled: false`; тогда коммит получит сообщение «chore: применить патч <patchId>») |

`patchId` должен быть новым для каждого патча: патч с идентификатором уже применённого `start`
пропустит как применённый. Исправленную версию упавшего патча можно прислать с тем же `patchId`.

### Все поля

| Поле | Действие |
| --- | --- |
| `createdAt` | ISO-время; участвует в упорядочивании патчей и в хронологии `devctl zip` |
| `kind` | произвольная пометка; devctl не использует |
| `base.branch` | если задано, `start` требует, чтобы проект был на этой ветке |
| `base.expectedHead` | SHA (не короче 7 символов), против которого собран патч; если HEAD проекта другой, `start` останавливается до любых изменений |
| `base.after` | `patchId` или список `patchId`, которые должны быть применены раньше. Если такой патч лежит в той же очереди `patches/`, `start` возьмёт его первым; если его нет ни в очереди, ни в истории, `start` остановится |
| `target.projectId`, `target.workspaceId`, `target.projectName`, `target.expectedFiles` | подсказки для `devctl inbox`: в какой workspace доставить патч |
| `apply.filesRoot` | каталог с файлами внутри zip; по умолчанию `files` |
| `apply.delete[].path` | относительный путь для удаления |
| `apply.delete[].recursive` | `true`, чтобы удалить каталог |
| `apply.delete[].required` | `true` — ошибка, если пути нет; иначе только предупреждение |
| `checks[].name`, `checks[].cwd`, `checks[].command` | обязательны для каждой проверки; `cwd` — каталог внутри проекта или `.` |
| `checks[].timeoutSeconds` | положительное целое; по умолчанию 300 |
| `checks[].requiredCommands` | программы, которые должны находиться в `PATH`; проверяется до применения |
| `commit.message` | сообщение коммита; devctl добавит трейлеры `Patch-Id`, `Patch-SHA256`, `Devctl-Version` |
| `push.remote`, `push.branch` | цель push; иначе берутся `git.remote` и `git.branch` workspace |
| `archive.nameSlug` | имя в названиях каталога запуска, снимков и копии `UserTestSpace`. Без него снимки и копия берут `patchId`, а каталог запуска — слово `patch`; задавайте его всегда |
| `archive.exclude` | дополнительные исключения для снимков; `!шаблон` возвращает путь в снимок |
| `archive.includeProjectDir` | `false` — класть файлы в корень снимка без каталога проекта |
| `archive.includeReleasePayloads` | `true` — включать в снимки `release/*.zip` и `release/*.exe` |

### Поля, которые не работают так, как можно подумать

- `commit.enabled: false` и `push.enabled: false` игнорируются: `start` всё равно коммитит и пушит,
  а в отчёт попадает предупреждение. Отключить push может только владелец workspace — флагом
  `--no-push` или настройкой `git.autoPush`.
- `commit.allowEmpty: true` пустого коммита не создаёт: если патч не дал изменений, `git commit`
  завершится ошибкой и запуск будет считаться упавшим. Без этого поля такой запуск считается
  применённым, коммит просто пропускается.
- `setup` и `services` зарезервированы. Непустой список — ошибка: devctl не ставит зависимости и не
  запускает сервисы.
- `checks: []` допустим: запуск пройдёт с предупреждением об отсутствии проверок.

## Правила для путей

- Только относительные POSIX-пути: без `\`, без ведущего `/`, без сегментов `.`, `..` и пустых, без
  буквы диска в начале.
- Файлы из `files/`: нельзя писать в `.git` и нельзя приносить `.env` и `.env.*`. Исключение —
  шаблоны без секретов: `.env.example`, `.env.sample`, `.env.template`, `.env.dist`. Если такой шаблон
  скрыт `.gitignore` проекта, в отчёт попадёт предупреждение: файл скопирован, но в коммит не попадёт.
  `devctl inbox` строже: он не примет патч с путём, в котором есть `.devctl`, `target`
  или `node_modules`.
- `apply.delete`: нельзя удалять пути с компонентом `.git`, `.devctl`, `target`, `node_modules` и сам
  корень проекта.
- `__pycache__/`, `*.pyc`, `*.pyo` из `files/` молча не копируются; патч, в котором нет ничего другого,
  считается некорректным.
- Патч без единого файла и без удалений некорректен.

Перед коммитом действует ещё один фильтр — см. шаг 7 и раздел об ограничениях в
[pipeline.md](pipeline.md): если `git status` показывает сгенерированные файлы, `start` остановится.

## Проверки

Команда выполняется через оболочку в каталоге `cwd`; ненулевой код возврата или истечение
`timeoutSeconds` останавливают запуск и откатывают проект. Проверки идут по порядку до первой неудачи.
Вывод каждой сохраняется в `logs/check-NN-<слаг имени>.log`.

Каталог `cwd` должен существовать до применения патча или появиться в результате него: предполётная
проверка принимает каталог, внутри которого в `files/` есть хотя бы один файл. Если каталога нет и после
наложения, проверка считается упавшей.

Хорошая проверка не оставляет следов в проекте. Для Python: `python -B …` и
`python -c "import ast, pathlib; ast.parse(pathlib.Path('x.py').read_text(encoding='utf-8'))"` вместо
`py_compile`.

## PATCH_SUMMARY.md

Свободный текст: что сделано, почему, что проверено, что осталось. devctl его не разбирает, но
`devctl zip` помещает текст в шаг истории рядом с диффом — по этим сводкам читатель архива
восстанавливает ход работы. Первые строки ценнее всего: при тесном бюджете сводка обрезается с конца,
а читаются из неё только первые 256 КиБ.

## Памятка для того, кто готовит патч

1. Положить в `files/` полные новые версии изменённых и новых файлов.
2. Перечислить удаляемые пути в `apply.delete`.
3. Дать новый `patchId`, осмысленные `title` и `summary`.
4. Указать проверки, которые действительно доказывают работоспособность и выполняются на машине
   владельца без установки чего-либо.
5. Приложить `PATCH_SUMMARY.md`.
6. Не класть в патч `.env`, bytecode, сборочные каталоги и базы данных.

Полный пример — [patch-manifest.example.json](patch-manifest.example.json).
