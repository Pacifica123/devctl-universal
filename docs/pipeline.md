# Конвейер `devctl start`

`start` применяет один патч — последний неприменённый — и либо доводит его до коммита, либо возвращает
проект в исходное состояние. Этот документ описывает, что именно происходит и что остаётся на диске.

## Шаги

1. **Поиск workspace и патча.** Кандидаты — все `*.zip` в `patches/`. Берётся самый свежий из тех, что
   ещё не применялись, с поправкой на `base.after` (см. [commands.md](commands.md#start)); `--patch`
   задаёт файл явно. Если таких нет, `start` сообщает об этом и завершается с кодом 0.
2. **Проверка патча.** Манифест, пути внутри zip, наличие хотя бы одного файла или удаления.
3. **Предполётная проверка.** До любых изменений на диске:
   - `git` доступен, проект — репозиторий;
   - рабочее дерево чистое;
   - текущая ветка совпадает с `manifest.base.branch`, если она указана;
   - HEAD начинается с `manifest.base.expectedHead`, если он указан;
   - патчи из `manifest.base.after` уже применены (журнал или трейлеры `Patch-Id` в истории);
   - если push включён и ветка в remote уже есть — локальная ветка не отстаёт, не опережает и не
     разошлась с ней (перед сравнением выполняется `git fetch`);
   - рабочие каталоги проверок существуют или создаются патчем, команды из `requiredCommands`
     находятся в `PATH`.
4. **Каталог запуска** `archives/<YYYYMMDD_HHMMSS>_<nameSlug>_<sha7 патча>/` и снимок «до» (`pre_*.zip`).
5. **Применение.** Сначала удаления из `apply.delete`, затем файлы из `files/` поверх проекта.
   Python bytecode из патча не копируется.
6. **Проверки** из `manifest.checks` по порядку, каждая через оболочку в своём `cwd`, с таймаутом
   (`timeoutSeconds`, по умолчанию 300). Первая ненулевая завершает запуск. После проверок удаляются
   `__pycache__/`, `*.pyc`, `*.pyo`.
7. **Commit.** `git add -A` и коммит с сообщением из `manifest.commit.message` и трейлерами:

   ```text
   Patch-Id: <patchId>
   Patch-SHA256: <sha256 файла патча>
   Devctl-Version: <версия>
   Devctl-Batch: <batchId>        # только при запуске из пачки
   ```

   Перед коммитом `start` останавливается, если в строках `git status` есть сгенерированные или
   локальные файлы: `.env`, `.env.*` (кроме шаблонов `.env.example`, `.env.sample`, `.env.template`,
   `.env.dist`), `*.db`, `*.sqlite`, `*.sqlite3`, `*.pyc`, `*.pyo` либо путь с
   компонентом `node_modules`, `target`, `.git`, `__pycache__`, `patches`, `archives`, `UserTestSpace`.
   Исключение — чистое удаление уже отслеживаемого bytecode.
   Если после патча и проверок изменений нет, коммит и push пропускаются, а запуск считается
   применённым.
8. **Push** `git push <remote> HEAD:<branch>`, если он не отключён (`--no-push`, `git.enabled=false`
   или `git.autoPush=false` в конфигурации workspace).
9. **Снимок «после»** (`post_*.zip`) и его распаковка в
   `UserTestSpace/project_<время>_after_<slug>_<sha7 коммита>/project`. Если коммита не было, в имени
   стоит sha7 файла патча.
10. **Отчёт** `report.md` и запись в `.devctl/state.json`.

## Статусы запуска

| Статус | Когда | Что с проектом | Код |
| --- | --- | --- | --- |
| `applied` | всё прошло | новый коммит (или без изменений) | 0 |
| `failed` | проверка, `git add` или `git commit` завершились ошибкой; найдены опасные файлы | автоматический откат | 1 |
| `push_failed` | коммит создан, push не удался | коммит остаётся, отката нет | 1 |
| `invalid_patch` | манифест или пути некорректны | не тронут; если применение уже началось — откат | 2 |
| `preflight_failed` | не прошла предполётная проверка | не тронут | 2 |
| `interrupted` | Ctrl+C | откат, если применение началось и коммита ещё нет | 130 |

## Автоматический откат

При `failed`, а также при `invalid_patch` и `interrupted` после начала применения:

1. сохраняется снимок сломанного состояния `failed_*.zip` (при `invalid_patch` снимок не делается);
2. выполняются `git reset --hard HEAD` и `git clean -fd`;
3. файл патча удаляется из `patches/` (отключается флагом `--keep-failed-patch`).

При `push_failed` отката нет: локальный коммит уже существует, и разбирать его нужно вручную; снимок
`failed_*.zip` при этом тоже сохраняется. Ручной откат — `devctl reset`.

## Что остаётся в каталоге запуска

```text
archives/20260101_120000_my-change_ab12cd3/
  report.md
  logs/
    manifest.json                       # копия манифеста
    git-status-before.log
    git-status-after-apply.log
    git-status-after-checks.log
    git-status-after-auto-reset.log     # только после отката
    check-01-<имя проверки>.log         # команда, каталог, код возврата, stdout, stderr
  pre_<проект>_<время>_before_<slug>.zip
  post_<проект>_<время>_after_<slug>_<sha7 коммита>.zip        # при успехе
  failed_<проект>_<время>_after_failed_<slug>.zip              # при ошибке
  failed_<проект>_<время>_after_interrupted_<patchId>.zip      # при Ctrl+C
```

`<slug>` в именах снимков и копии `UserTestSpace` — `archive.nameSlug` из манифеста или `patchId`.
В имени самого каталога запуска без `archive.nameSlug` стоит слово `patch`. Имя лога проверки —
её название, приведённое к латинице, цифрам и дефисам; название целиком на кириллице даёт
`check-01-patch.log`. Метки времени в именах — местное время машины.

## Что входит в снимки

Все файлы проекта, кроме:

- путей с компонентом `.git`, `target`, `node_modules`, `dist`, `build`, `coverage`, `logs`, `tmp`,
  `patches`, `archives`, `UserTestSpace`, `__pycache__`;
- файлов `.env` и `.env.*` (шаблоны `.env.example`, `.env.sample`, `.env.template`, `.env.dist` в снимок входят), `*.db`, `*.sqlite`, `*.sqlite3`;
- того, что перечислено в `manifest.archive.exclude`;
- `release/*.zip` и `release/*.exe`: вместо них в снимок кладётся текстовая заглушка с перечнем и
  размерами (отключается `archive.includeReleasePayloads: true`).

`build/pyinstaller.spec` входит в снимок всегда. Шаблон с `!` в начале в `archive.exclude` возвращает
путь в снимок. Внутри zip файлы лежат в каталоге с именем проекта (`archive.includeProjectDir: false`
убирает его). Снимок больше 100 МиБ даёт предупреждение в отчёте.

Список `archive.exclude` из `.devctl/workspace.json` применяется к снимкам `devctl sync` и к сравнению
деревьев в `devctl zip`; снимки `start` используют встроенный список и исключения из манифеста.

## UserTestSpace

Каждый успешный `start` и каждый `sync` распаковывает свежий post-снимок в новый каталог
`UserTestSpace/project_<время>_after_<slug>_<sha7>/project`. Здесь можно запускать сборки и ручные
проверки, не загрязняя проект. Старые каталоги devctl не удаляет.

## Журнал `.devctl/state.json`

Каждый завершённый запуск добавляет запись: `patchId`, `patchFile`, `patchSha256`, `status`,
`startedAt`, `finishedAt`, `commitSha`, `archiveDir`, `report`, сведения об автоматическом откате,
удалении плохого патча, копии в `UserTestSpace` и очистке bytecode. По этому журналу `start` узнаёт уже
применённые патчи, `reset` — последний упавший, а `devctl zip` восстанавливает запуски, каталоги
которых были удалены из `archives/`.

## Известные ограничения конвейера

Найдены при сверке документации с кодом 0.8.0; поведение унаследовано от прежних версий.

- **Фильтр перед коммитом видит не всё.** Он разбирает краткий `git status`, а тот показывает целиком
  новый каталог одной строкой. Файл `*.db` или каталог `node_modules` внутри нового каталога будут
  закоммичены. Фильтр срабатывает на изменения в уже существующих каталогах.
- **Первый патч в репозитории без коммитов не откатывается.** `git reset --hard HEAD` там невозможен:
  после упавшей проверки файлы патча останутся в проекте, а патч — в `patches/`. Сделайте начальный
  коммит до первого `start`.
- **`commit.allowEmpty`** пустого коммита не создаёт — см. [patch-format.md](patch-format.md).

## Что devctl не делает

- Не устанавливает зависимости и не запускает сервисы: разделы манифеста `setup` и `services`
  зарезервированы и должны быть пустыми.
- Не применяет несколько патчей за один запуск.
- Не чистит `archives/` и `UserTestSpace/`: их объёмом управляет владелец workspace.
