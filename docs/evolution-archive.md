# Эволюционный архив: `devctl zip`

`devctl zip` сжимает всю историю workspace в один zip с текстом, который можно целиком отдать
нейросети. Архив отвечает на вопрос «как этот проект и всё вокруг него дошли до нынешнего состояния»:
что менял каждый патч, какие запуски упали и почему, какие заметки и материалы появлялись между
патчами.

```bash
cd my-space
devctl zip
# → my-space_evolution_20261004_161500.zip в корне workspace
```

Команда только читает workspace. Единственное, что она создаёт, — сам архив.

## Что попадает в архив

Просматривается весь workspace, а не только каталоги, о которых знает devctl:

| Источник | Как используется |
| --- | --- |
| Git-история проекта | цепочка состояний: коммиты первой родительской линии `HEAD` |
| `patches/` и любые другие zip с `manifest.json` | сводка, `PATCH_SUMMARY.md`, привязка к состоянию |
| `archives/<запуск>/` | статус запуска, проверки, хвост лога упавшей проверки |
| `.devctl/state.json` | запуски, каталоги которых уже удалены из `archives/` |
| снимки `pre_`/`post_`/`failed_` и копии `UserTestSpace` | свидетели состояний; копии с ручными правками |
| ручные копии проекта (`stables/v1` и подобные) | то же: узнаются по составу верхнего уровня |
| всё остальное — заметки, каталоги с материалами, чужие архивы | события в общей хронологии |
| незакоммиченные изменения проекта | последний шаг «рабочее дерево» |

Не просматриваются `.git`, `.devctl`, прежние эволюционные архивы и служебные каталоги
`__pycache__`, `node_modules`, `.venv`, `venv`, `.tox`, `.pytest_cache`, `.mypy_cache`, `.ruff_cache`,
`.idea`, `.vscode`.

## Как устроено сжатие

Workspace велик потому, что одно и то же дерево файлов лежит в нём много раз: в коммите, в post-снимке,
в pre-снимке следующего запуска, в `UserTestSpace`, в ручной копии. Сжатие строится на том, чтобы
описать каждое уникальное содержимое ровно один раз.

1. **Состояния вместо копий.** Каждое дерево файлов получает отпечаток: набор пар «путь + ключ
   содержимого». Ключ — идентификатор Git blob, окончания строк CRLF/LF не различаются. Копии с
   одинаковым отпечатком — одно состояние с несколькими свидетелями. Сто копий проекта, появившихся
   после ста патчей, превращаются в сто состояний, а не в двести–триста деревьев.
2. **Цепочка отличий.** Состояния выстраиваются по порядку, и каждое описывается только отличием от
   предыдущего: какие файлы добавлены, изменены, удалены, переименованы.
3. **Свёртка по смыслу.**
   - переименование без изменения содержимого — одна строка `R старый → новый`;
   - 25 и более новых файлов в одном каталоге верхнего уровня — строка `A+` с перечнем путей,
     сгруппированным по каталогам; тела таких файлов показываются в последнюю очередь;
   - строки, в которых поменялись только хэши, сворачиваются в счётчик;
   - двоичные файлы — путь, размер и ключ;
   - изменение только хвостовых пробелов и окончаний строк — одна пометка.
4. **Копии с правками.** Копия, не совпавшая ни с одним состоянием, описывается как ближайшее
   состояние плюс её собственные отличия. Так видно, что владелец менял в `UserTestSpace` руками.
   Снимок `failed_` — тупиковая ветка: в цепочку он не входит.
5. **Материалы вокруг проекта.** Заметки — текстовые файлы `.md`, `.txt`, `.rst`, `.adoc`, `.org` и
   любые текстовые файлы до 4 КиБ — включаются с содержимым. Каталог со множеством
   файлов сворачивается в одну запись: число файлов, объём, типы, состав. Посторонний zip — в строку с
   числом файлов и верхним уровнем. Двоичные и большие файлы — имя и размер.

## Хронология

Все события стоят в одном ряду и пронумерованы насквозь: состояния проекта, запуски без результата,
патчи без следа применения, ручные копии, заметки и материалы. По `TIMELINE.md` видно, что заметка
появилась после одного патча и перед другим.

Время события:

| Событие | Откуда время |
| --- | --- |
| коммит | время коммита |
| запуск | время старта из `report.md` или из журнала; если их нет — метка в имени каталога |
| снимок, копия `UserTestSpace` | метка `YYYYMMDD_HHMMSS` в имени — местное время машины, записанное devctl |
| ручная копия проекта | метка `YYYYMMDD_HHMMSS` в её пути, если есть; иначе самый свежий файл в ней. Не раньше состояния, которое она повторяет |
| патч без применения | `createdAt` манифеста, метка в имени, иначе время изменения файла |
| прочие файлы | время изменения (mtime); у свёрнутого каталога — самый ранний файл |

Порядок состояний задаёт Git, а не часы: если время коммитов идёт не по порядку, цепочка всё равно
следует истории. После переноса workspace на другую машину mtime посторонних файлов может оказаться
временем копирования — тогда их место в хронологии сдвинется; коммиты и метки в именах от переноса
не зависят. Время печатается в часовом поясе машины, на которой собран архив.

## Привязка патчей к состояниям

По убыванию надёжности:

1. трейлеры `Patch-Id` и `Patch-SHA256` в сообщении коммита;
2. журнал запусков: успешный запуск знает и патч, и коммит;
3. совпадение содержимого — первое состояние, в котором все файлы патча присутствуют одновременно.

Способ, отличный от первого, указан в файле шага. Патч, для которого не нашлось ничего, показан как
«патч без следа применения» на месте по своему времени. Упавший запуск и сохранившийся файл его патча
— одно событие.

## Если истории Git нет

Проект мог переехать без `.git` или история могла начаться заново. Тогда цепочка состояний строится
из того, что чисто по построению: архивов-снимков и копий `UserTestSpace`, созданных devctl. Копия
`UserTestSpace` не становится звеном цепочки, если от того же состояния сохранился архив или если в ней
есть файлы моложе её собственной метки больше чем на 10 минут — значит, в ней работали руками; такая
копия описывается как состояние с локальными правками. Если «моложе метки» оказалось больше половины
копий, признак не применяется: так выглядит перенос, сбросивший время файлов. Если чистых кандидатов
нет вовсе, цепочка строится по всем найденным копиям-каталогам. Снимки, сделанные раньше первого
коммита, продолжают цепочку назад.

Применённый запуск, от состояния которого не осталось ни коммита, ни копии, показан как «патч
применён, состояние не сохранилось»: его изменения входят в отличие следующего сохранившегося
состояния.

## Бюджет

Объём текста задаётся уровнем или числом:

| Уровень | Бюджет | Примерно токенов | Для чего |
| --- | --- | --- | --- |
| `brief` | 256 КиБ | 80 тыс. | каркас истории и начала сводок |
| `normal` | 512 КиБ | 160 тыс. | окно 200 тыс. токенов; по умолчанию |
| `full` | 2 МиБ | 650 тыс. | окно 1 млн токенов |
| `max` | без ограничения | — | все диффы и тексты целиком |

`--budget-kb N` задаёт бюджет точно. Оценка токенов грубая: 3,2 байта на токен.

На любом уровне строки длиннее 320 символов обрезаются, из `PATCH_SUMMARY.md` читаются первые 256 КиБ,
а от лога упавшей проверки берутся последние 24 непустые строки.

Текст делится на каркас и три класса содержимого.

- **Каркас** печатается всегда: `TIMELINE.md`, заголовки шагов, строка на каждый изменённый файл с
  числом добавленных и удалённых строк. Исключение — файлы массового добавления: их пути стоят в
  перечне, а отдельная строка появляется, только если поместилось тело. Каркас растёт с числом
  событий; если бюджет меньше каркаса, `devctl zip` выдаёт каркас и предупреждает об этом.
- **Повествование** — `PATCH_SUMMARY.md`, заметки, перечни файлов массовых добавлений — получает до
  60% остатка. Текст обрезается с конца: начало сводки сохраняется.
- **Диффы** получают следующую долю. Чем ближе шаг к концу истории, тем больше строк: недавние диффы
  видны телом, давние — перечнем затронутых функций, классов и заголовков. Исходный код получает
  больше строк, чем документация, тесты и данные; изменение файла — больше, чем добавление нового.
- **Массовые добавления** — первый импорт, вендоренный код — берут оставшееся, но за ними придержана
  десятая часть, и подробнее обычных диффов они не бывают.

Неистраченное достаётся сначала диффам, затем повествованию, затем массовым добавлениям. Каждое
сокращение помечено в тексте: `… опущено строк: N из M`, `(затронуто: …; строк: N)` или строка
статистики без тела.

`--with-final` дополнительно кладёт в `final/` текстовые файлы итогового состояния проекта, кроме
файлов больше 512 КиБ. Они не входят в бюджет.

## Формат архива

```text
<workspace>_evolution_<YYYYMMDD_HHMMSS>.zip
  README.md        # как читать, что вошло, как сжато, как достать опущенное, итоговое дерево
  TIMELINE.md      # вся хронология: одна запись на событие
  steps/
    0001_<slug>.md # подробности события 0001
    …
  index.json       # машинный указатель
  final/…          # только с --with-final
```

Запись хронологии:

```text
- **0042** · 2026-08-13 14:05 · ПАТЧ · v04-stage8i — TXT preset import · commit 1a2b3c4 · файлов 9 (+3 ~6) →
  - Краткая сводка из манифеста.
```

Стрелка в конце означает, что есть файл `steps/0042_*.md`. В нём:

```text
# 0042 · 2026-08-13 14:05 · ПАТЧ · v04-stage8i — TXT preset import

- commit: `1a2b3c4d5e6f`
- патч: `patches/patch_z2guiflin_20260813_v04-stage8i-txt-preset-import.zip`
- запуск `archives/20260813_140455_…`: applied · Тесты: успех
- точные копии: `stables/v0.4-stable`, UserTestSpace ×1, архивы-снимки ×2

## PATCH_SUMMARY.md
…
## Изменения: файлов 9 (+3 ~6)

- M gui/main_window.py (+38 −4)
  (дифф или перечень затронутых объявлений)
- A presets/import_txt.py (+120 строк)
- R docs/OLD.md → docs/history/OLD.md

## Копии этого состояния с локальными изменениями
…
```

Виды событий: `ПАТЧ`, `КОММИТ` (без патча), `СНИМОК` (состояние без Git), `РАБОЧЕЕ ДЕРЕВО`,
`ЗАПУСК БЕЗ РЕЗУЛЬТАТА`, `ПАТЧ ПРИМЕНЁН, СОСТОЯНИЕ НЕ СОХРАНИЛОСЬ`, `SYNC`, `ПАТЧ БЕЗ СЛЕДА ПРИМЕНЕНИЯ`,
`КОПИЯ ПРОЕКТА`, `АРХИВ-СНИМОК`, `ФАЙЛ`, `ФАЙЛЫ`, `КАТАЛОГ`.

`index.json` содержит версию формата (`"devctlEvolution": 1`), сведения о workspace и Git, статистику
сборки и таблицу состояний: номер, вид, время, коммит, патчи, файл шага, число копий.

## Как достать опущенное

Архив не заменяет workspace: он ссылается на него.

- файл на момент коммита: `git -C <проект> show <commit>:<путь>`;
- двоичный файл по ключу: `git -C <проект> cat-file -p <ключ>` — ключ есть начало идентификатора
  Git blob; так достаётся только то, что есть в истории Git, но не содержимое, встреченное лишь в
  копиях и снимках;
- состояние целиком: `UserTestSpace/project_<время>_after_<slug>_<коммит>/project` или `post_*.zip`
  в каталоге запуска;
- всё сразу: `devctl zip --level max`.

## Границы

- **Секреты не вычищаются.** В архив попадают диффы, заметки, сообщения коммитов, логи проверок,
  абсолютные пути и адрес remote (без встроенных в URL учётных данных). Что есть в workspace, то может
  оказаться в архиве; за его распространение отвечает владелец.
- Из Git берётся только первая родительская линия `HEAD`. Другие ветки и теги в цепочку не входят;
  их число указано в `README.md` архива.
- Переименования распознаются только при неизменном содержимом; переименование с правкой выглядит как
  удаление и добавление.
- Содержимое двоичных файлов, файлов больше 1,5 МБ и посторонних zip не включается. Заметка больше
  256 КиБ считается обычным файлом: имя и размер.
- Снимки, из которых патч исключил пути через `archive.exclude` сверх списка workspace, выглядят как
  копии, в которых этих путей нет.
- Файлы больше 64 МиБ сравниваются только по размеру: изменение такого файла без изменения размера
  останется незамеченным.
- Каркас не сжимается под бюджет: у workspace с тысячами событий одна хронология займёт сотни килобайт.

## Скорость и объём

Замер сделан при разработке 0.8.0 на синтетическом workspace, собранном настоящим `devctl start` по
образцу реального: 2,1 ГиБ, 75 тысяч файлов, 110 применённых патчей, 12 упавших запусков, 357 копий
проекта, каталоги посторонних материалов, zip на 700 МиБ. В репозитории этого стенда нет.

| Уровень | Текст | Архив | Сжатие |
| --- | --- | --- | --- |
| `brief` | 252 КиБ | 134 КиБ | в 16 000 раз |
| `normal` | 502 КиБ | 215 КиБ | в 10 000 раз |
| `full` | 2,0 МиБ | 613 КиБ | в 3 500 раз |
| `max` | 7,8 МиБ | 2,0 МиБ | в 1 000 раз |

Сборка любого уровня заняла около 8 секунд. Время определяется числом и размером копий проекта: каждая
копия-каталог читается целиком, члены архивов-снимков и патчей с уже встречавшимися CRC и размером не
распаковываются. Посторонние материалы почти не читаются: у файла до 256 КиБ — первые 8 КиБ, чтобы
отличить текст от двоичных данных, заметки — целиком, у zip — только оглавление; у каждого патча
считается SHA-256. Тяжёлые файлы рядом с проектом на время почти не влияют.
